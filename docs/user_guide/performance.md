# Performance

## Compilation

The first call to `Simulation.run` for a given configuration traces the Python code
and compiles it with XLA. Compilation takes a few seconds on a workstation and is
paid once per static configuration per Python process. Subsequent calls with the same
static parameters, including calls with different differentiable inputs, run the
compiled program directly. A changed particle count, grid size, step count, algorithm
switch, boundary condition, filter setting or seed triggers a new compilation.

In a script that runs many simulations, keep one `Simulation` object and vary the
physics through the runtime inputs of `run` (see {doc}`running`). The drift-speed scan
in {doc}`../numerics/verification` runs nine simulations and compiles once.

## Cost per step

The explicit scheme performs, per step, two current deposits, one charge deposit,
two half field updates, one field interpolation and one Boris push over all particles.
Deposition dominates. It is written as a `vmap` over particles of a function that
evaluates the spline on the whole grid and sums the result over particles, which
compiles to dense array operations rather than scatter-adds: the cost is proportional
to the product of the number of particles and the number of cells, not to their sum.
Doubling the grid at fixed particle number therefore nearly doubles the run time, as
panel (b) below shows. The field updates and the filter are linear in the number of
cells and negligible in comparison.

The GPU here is a workstation card whose double-precision throughput is a small
fraction of its single-precision one, and the package runs in double precision (see
below), so a data-centre GPU or single precision changes the balance. Both machines were
shared while the timings were taken, which is visible as scatter at small $N$.

The implicit scheme costs one particle push per sub-step per Picard iteration, so with
the defaults (two sub-steps, a few iterations to converge) it is several times more
expensive per step than the explicit scheme. It compensates by allowing larger steps
when the light-wave limit is what constrains the explicit scheme.

## Precision

The package switches JAX to 64-bit floating point when it is imported, overriding
the `JAX_ENABLE_X64` environment variable. Single precision runs faster on GPUs and
halves the memory, but the accumulated energy error and the noise floor of the
instabilities are visibly worse. To try it, switch the flag back after the import,

```python
import jax, jaxincell
jax.config.update("jax_enable_x64", False)
```

before constructing a `Simulation`; every array in the output is then `float32`. The
external field arrays are stored in single precision regardless.

## Memory

All `total_steps` states are kept, see {doc}`output`. The particle histories dominate:
$2 \times 3 \times 8 \times N \times S$ bytes for $N$ particles over $S$ steps in double
precision. With reverse-mode differentiation the residuals of the scan are stored in
addition.

## Devices

JAX places arrays on its default device. With a CUDA build of `jaxlib` installed the
simulation runs on the GPU without any change to the script. To force the CPU, set
`JAX_PLATFORMS=cpu`. Multi-device execution is not implemented: one simulation runs on
one device.

## Progress bar

`jax_tqdm` draws a progress bar from inside the compiled loop. It is useful in a
terminal and harmless in a batch job, but it can be switched off by setting the
environment variable `TQDM_DISABLE=1`.
